# Компромиссы: Live Activity, релей, лендинг, демон, установка интеграций

## Live Activity агентов

**Решение:** Её стартует, обновляет и закрывает `wierdrd` на Mac через APNs: push‑to‑start на токен
устройства (токен приложение кладёт в документ `wierdr-push` ядра), обновления и конец — broadcast
на канал (iOS 18), у каждой активности свой. Сервера нет: «сервер» — сам Mac. Подробно:
[live-activity.md](../live-activity.md)

**Почему / цена:** Приложение в фоне не может держать SSH, а Live Activity сама в сеть не ходит;
остаются только пуши. Канал вместо токена каждой активности: иначе приложению пришлось бы в фоне,
разбуженным после push‑to‑start, подключаться по SSH, чтобы сообщить токен. **Цена:** нужен
APNs‑ключ `.p8` и галка Broadcast у App ID; Mac должен не спать (иначе через 25 мин «Not updated»);
только iPhone; демон — на том компьютере, к которому подключается телефон. Смахнутая активность
возвращается, когда откроешь Wierdr (он сообщает, что её нет), иначе — только со следующим стартом.
Каждый start по пушу обязан нести alert (без него ActivityKit активность не создаёт), а alert
вибрирует: поэтому в простое активность держится ещё 2 ч, показывая «idle», и запуск агента за это
время — обычное обновление.

## Live Activity: печать

**Решение:** Пуши запечатаны всегда: открыты счётчики и время, агенты (заголовки, спейсы, модели,
машины, адреса) и атрибуты (имя компьютера) — `AES-GCM(zlib(JSON))` ключом демона. Ключ — в
документе `wierdr-push-seal` ядра, телефон кладёт его файлом в App Group, виджет читает по `kid`.
Alert без имён: «Needs you» / «Done» и счётчики. Подробно:
[live-activity.md](../live-activity.md#запечатано)

**Почему / цена:** Пуши идут через APNs, а с App Store — и через наш релей
([research/push-relay.md](../research/push-relay.md)); над пушем Live Activity нет своего кода, кроме
`init(from:)` в виджете, значит открыть печать может только он. Связки ключей у Live Activity на
iPhone нет (проверено дважды), файл в App Group есть, и на заблокированном телефоне. Счётчики
открыты, чтобы без ключа активность всё равно говорила, сколько ждут и работают. **Цена:** нужен App
Group у обоих App ID; пока Wierdr не подключился к компьютеру (новый телефон, сменённый ключ),
вместо строк «Open Wierdr to see the agents»; часы в alert не показывают, кто ждёт; Apple видит
счётчики, время и частоту пушей.

## Релей пушей

**Решение:** Cloudflare Worker (`Relay/`, `relay.wierdr.workat.dev`, тариф Free): демон шлёт ему
start, broadcast и запросы каналов, он подписывает нашим ключом APNs. Права — строки HMAC без
хранения, названные ключом App Attest владельца (устройства — на токен, приложение получает через
App Attest; канала — с каналом), продлеваются, пока ими пользуются; ключ можно отозвать. Пропускает
только пуши Wierdr нужного вида (поля, alert — слова Wierdr и строка тех же счётчиков), записанные
заново. D1 — ключи App Attest, токены по ключам, учёт каналов, счётчики, общий JWT. Подробно:
[relay.md](../relay.md)

**Почему / цена:** Копии из App Store шлёт только ключ команды, свой ключ пользователю не поможет
([research/push-relay.md](../research/push-relay.md)). Worker: исходящий `fetch` к APNs идёт по HTTP/2
(проверено), Custom Domain с сертификатом, D1, cron и лимиты — без своих серверов. App Attest —
чтобы права раздавались только настоящему Wierdr. Квоты на ключ (5 токенов, 30 каналов в сутки, 6
живых и 2, пока APNs не принял старт на его токен, вытеснение самого старого) и суточный бюджет
новых ключей (1000) — чтобы и много ключей со взломанного телефона не забили 10 000 каналов
приложения у APNs надолго. Учёт каналов в D1 и cron — потому что канал живёт, пока его не удалят.
**Цена:** свой сервис — если он лежит, Live Activity не обновляется ни у кого; на Free 100 000
запросов в сутки на всех; бюджет аттестаций можно выбрать за день, и тогда новые установки ждут до
завтра; пуш — два чтения D1 (отзыв), старт ещё и запись; локальный `wrangler dev` не достаёт до APNs
(только тесты с подменой); в симуляторе App Attest нет — через релей пушей туда нет; alert — только
слова Wierdr.

## Лендинг

**Решение:** Одна статическая страница на английском (`Site/`, `wierdr.workat.dev`) на Cloudflare
Workers со статикой, без сборки, внешних шрифтов и скриптов; призыв — публичная бета в TestFlight и
GitHub («Coming soon to the App Store» — строкой), без waitlist. Подробно: [site.md](../site.md)

**Почему / цена:** Тот же аккаунт и домен, что у релея, и тот же `wrangler`; Workers, а не Pages:
Cloudflare ведёт статику туда. Страница рекламная: зацепить, подробности — в README. Waitlist — это
хранение адресов (политика, GDPR) ради того, что даст и звёздочка на GitHub. **Цена:** до выхода в
App Store — только бета в TestFlight (её места и сроки ограничены Apple); скриншоты обновляются
руками (`images.sh`).

## Демон на Mac: wierdrd

**Решение:** Демон Wierdr (бывший `wierdr-push`) — формула Homebrew в тапе `wierdbytes/apps`
(репозиторий `wierdbytes/homebrew-apps`); бинарь — готовый, universal, в релизах Wierdr, формулу в
тап пишет CI. Приложение ставит и запускает его само: после первого подключения к хосту — лист «Set
Up wierdrd» (iPad и iPhone), потом Settings → Daemon. Проба и действия идут через `machine.exec`
ядра; без `push.json` демон ходит через релей. Подробно: [wierdrd.md](../wierdrd.md)

**Почему / цена:** Формула, а не cask: только у формул есть `brew services` (LaunchAgent, KeepAlive,
вход), и загрузку формулы Homebrew не ставит в карантин, так что бинарь работает и без Developer ID.
Готовый бинарь, а не сборка из исходников: у пользователя не нужен Swift, установка занимает
секунды. Отдельный тап, а не этот репозиторий: короткий адрес (`wierdbytes/apps/wierdrd`, `brew tap`
без URL), `brew tap` клонирует маленький репозиторий, а не весь Wierdr, и тап годится для других
программ; цена — CI пишет в чужой репозиторий, для этого у тапа свой deploy key с записью (секрет
`HOMEBREW_APPS_DEPLOY_KEY`), а не личный токен. `machine.exec`, а не команда по SSH: она выполняется
в сессии ядра (Aqua), и `brew services` кладёт службу в `gui/<uid>`, как при входе; из SSH Homebrew
взял бы `user/<uid>`. Без Homebrew приложение только объясняет, что делать. Документы ядра
`wierdr-push` и `wierdr-push-seal` при переименовании не тронуты: это контракт данных с телефонами.

## Интеграции агентов из приложения

**Решение:** После первого подключения лист «Set Up <хост>» вместе с демоном предлагает интеграции в
найденные харнессы: pi-wierdr, `cc@wierdr`, `codex@wierdr` — командами самих харнессов
(`pi install`, `claude plugin …`, `codex plugin …`) через `machine.exec`, с `PATH` логин‑оболочки;
только харнессы, которые уже стоят и не старше нужного. Подробно: [host-setup.md](../host-setup.md)

**Почему / цена:** Команды харнессов, а не запись в их файлы: они сами ставят зависимости, кэш и
маркетплейс и переживут смену своих форматов. Исключение — проба Codex: `codex plugin list` тянет
удалённый каталог больше минуты, поэтому читается `config.toml`. `PATH` логин‑оболочки: харнессы
лежат там, куда их кладут их установщики (`~/.bun/bin`, `~/.local/bin`, npm, mise), а у ядра свой
`PATH`. Ставить сами харнессы, обновлять их или доверять хуки Codex приложение не берётся: это
решения человека в самом харнессе.
