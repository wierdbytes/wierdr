# Пуши с компьютеров пользователей: релей APNs

Вопрос: когда Wierdr будет в App Store, сможет ли пользователь у себя запустить сервер
(`wierdr-push` рядом с herdr-core), который шлёт пуши в приложение: Live Activity агентов,
обычные уведомления?

**Ответ: напрямую нет, через наш релей да.** Пуш в приложение из App Store подписывается
только ключом нашей команды. Сервер пользователя может решать, что и когда слать, а отправку
в APNs делает тонкий релей, который держим мы. Скрыть от релея содержимое Live Activity
пока не получилось: в симуляторе запечатанный `content-state` открывается в виджете, но на
iPhone у Live Activity нет связки ключей (проверено дважды, 16 и 19.11.2026). Остались два непроверенных
кандидата: ключ в App Group и расшифровка в самом приложении, которое передаёт
виджету готовое содержимое локальным `activity.update` (см. «Запечатанная Live Activity»).

## Почему напрямую нельзя

- APNs принимает пуш на topic `pw.xff.wierdr` только с JWT, подписанным `.p8`-ключом
  команды `AUL4CCB2XY`, или с сертификатом этого bundle id. Сейчас так подписывает
  `wierdr-push` на нашем Mac (`WierdrPush/APNs.swift`, ключ в `~/.config/wierdr/push.json`).
- Свой Apple Developer аккаунт пользователю не поможет: его ключ действует только для
  приложений его команды, а не для нашего bundle id.
- То же с API каналов (`api-manage-broadcast.push.apple.com`): каналы принадлежат
  приложению, создать и удалить их можно только нашим ключом.
- Firebase, OneSignal и т. п. не обходят это ограничение: туда загружают тот же наш ключ, а
  пользователю пришлось бы выдать доступ к нашему проекту.

С февраля 2025 Apple разрешает ограничить ключ одним окружением (sandbox или production) и
одним topic (bundle id). Если раздать такой ключ, утечёт меньше, но это всё равно наш ключ у
всех.

## Варианты

| Вариант | Как | Итог |
|---|---|---|
| **Релей у нас** | `wierdr-push` пользователя шлёт пуш нашему серверу, сервер подписывает его нашим ключом и отправляет в APNs | ✅ Так устроены ntfy (`upstream-base-url` → ntfy.sh), Home Assistant, Matrix (Sygnal у вендора клиента) |
| Ключ в открытом виде | Как у Bark: его ключ лежит в репозитории `bark-server` | ❌ Кто угодно сможет слать пуши любому пользователю. Отзыв ключа сломает всех |
| Сборка из исходников | Пользователь сам собирает Wierdr со своим bundle id и своим ключом | Только для энтузиастов, к App Store не относится |
| Без пушей | Фоновое обновление | ❌ Live Activity без пушей почти не обновляется, а фоновые обновления ненадёжны |

## Релей для Wierdr

```
iPhone (Wierdr) ──SSH──▶ Mac пользователя: herdr-core + wierdr-push ──HTTPS──▶ релей (наш) ──HTTP/2──▶ APNs
      ▲                                                                                              │
      └──────────────────────────────── Lock Screen / Dynamic Island ◀───────────────────────────────┘
```

- **API повторяет `APNsClient`.** Сейчас он умеет четыре операции: `start` (push-to-start на
  токен устройства), `broadcast` (update и end в канал), `createChannel`, `deleteChannel`.
  Релей принимает те же четыре. В `WierdrPush` появится протокол транспорта с двумя
  реализациями: `APNsClient` (свой ключ, наши dev-сборки) и `RelayClient` (по умолчанию для
  App Store). `Planner`, `ActivitySummary`, документ `wierdr-push` и схема регистрации не
  меняются.
- **Права без базы данных.** Приложение регистрирует push-to-start токен на релее и
  получает право на него: `grant = HMAC(секрет релея, токен ‖ env ‖ срок)`. Подлинность
  приложения проверяется через App Attest, чтобы права раздавались только настоящему
  Wierdr. Право ложится в запись устройства в документе `wierdr-push` рядом с токеном
  (`PushRegistry.Device`). Демон шлёт его с каждым `start`. Для каналов так же:
  `createChannel` возвращает id канала и право на него, а `broadcast` и `deleteChannel`
  требуют это право. Без права релей не отправит ничего ни на чужой токен, ни в чужой канал.
- **Ключ релея.** Отдельный `.p8`, ограниченный topic `pw.xff.wierdr` и окружением production.
- **Что релей проверяет:** только `apns-push-type: liveactivity` (потом и `alert`), размер
  не больше 4 КБ, лимиты на право и на IP. Бюджет пушей Apple считает на всё приложение,
  поэтому шумный пользователь задевает остальных. Ещё релей может принимать только
  запечатанный `content-state`.
- **Своё обслуживание.** Сервер должен работать всегда: если он упал, Live Activity не
  обновляется ни у кого. Нужны privacy policy и пункт в App Privacy (токены устройств идут
  на наш сервер).

Ещё не выяснено: есть ли у Apple предел числа каналов broadcast на приложение (у каждого
пользователя свои каналы). Об этом ничего не нашлось, нужно проверить до запуска.

## Запечатанная Live Activity

Обычные пуши можно шифровать от начала до конца: их расшифровывает Notification Service
Extension. Для Live Activity такого расширения нет: `content-state` уходит виджету без
нашего кода. Считалось, что поэтому её содержимое (заголовки агентов, спейсы, модели)
релей и Apple видят открытым текстом.

**Гипотеза:** ActivityKit хранит `content-state` и `attributes` как JSON, а в
`ContentState` их разбирает наш `init(from:)` в процессе виджета. Значит, туда можно
положить шифротекст и открыть его ключом из связки ключей, общей для приложения и
виджета.

**Итог: механизм работает, но на iPhone ключ до виджета не доходит.** Наш `init(from:)`
действительно разбирает пуш в процессе виджета. Но в песочнице, где рисуется Live
Activity, связка ключей на устройстве недоступна. Код лежит в ветке
`lab/sealed-live-activity`.

### Симулятор: работает

iOS 27.0, Xcode 27.1, настоящий APNs sandbox, приложение закрыто.

- Формат: `"content-state": {"sealed": base64(AES-GCM(zlib(JSON)))}`. `attributes`
  запечатаны так же. Демон пакует (`ActivityPayload` с `key:`), а
  `ContentState.init(from:)` распаковывает (`WierdrActivity/Sealed.swift`).
- Ключ хранится в группе связки ключей `$(AppIdentifierPrefix)pw.xff.wierdr.shared`
  (`keychain-access-groups` у приложения и виджета, профиль менять не нужно) с классом
  `AfterFirstUnlockThisDeviceOnly`, чтобы виджет мог рисовать на заблокированном телефоне.
- Если печать не открылась, виджет рисует строку «🔒 причина (статус связки) в процессе».
  Если открылась, первая строка помечена процессом, который её открыл.

| Шаг | Пуш | Что показал Lock Screen |
|---|---|---|
| push-to-start, всё запечатано, приложение закрыто | 931 Б | Содержимое расшифровано, у первой строки `🔓widgets`: печать открыло расширение `pw.xff.wierdr.widgets` |
| broadcast update, запечатан | 699 Б | Обновилось: «Update #1: sealed and opened» |
| update чужим ключом | 698 Б | «🔒 badSeal (keychain 0) in pw.xff.wierdr.widgets»: ключ из связки прочитан, печать не открылась |
| ключ удалён из связки | 706 Б | «🔒 noKey (keychain -25300)» |
| ключ возвращён, update | 703 Б | Снова расшифровано |
| broadcast end, запечатан | 699 Б | Активность ушла |

Лог `liveactivitiesd` подтверждает, что система сама ничего не разбирает: она получает
`attributesData: 83 bytes` и создаёт активность. Разбор идёт в виджете (и в приложении,
когда оно читает `Activity.activities`).

### iPhone: виджету недоступна связка ключей

iPhone 13 Pro Max, iOS 27.2.1, та же сборка (Release, development-подпись), настоящий APNs
sandbox, 16.11.2026. Чтобы узнать, был ли телефон заблокирован, каждый, кто открывает
печать, пишет строку в журнал в связке ключей (у виджета на iPhone и эта запись не
удаётся, его причина видна на самой активности). В строке есть статус пробы: элемента
`WhenUnlockedThisDeviceOnly`, который на заблокированном телефоне читается с `-25308`.
Снимок заблокированного экрана через `devicectl` выходит чёрным, поэтому состояние
проверялось через `/wda/locked` и журнал.

| Что | Результат |
|---|---|
| Виджет Live Activity читает ключ из общей группы связки | `errSecNotAvailable` (-25291) и на заблокированном, и на разблокированном телефоне. Активность рисует «🔒 noKey (keychain -25291) in pw.xff.wierdr.widgets» |
| Запасной ключ из `identifierForVendor` в виджете | `nil`: в этой песочнице его тоже нет |
| Приложение (висит в фоне) открывает те же пуши на заблокированном телефоне | Да. Журнал: «opened in pw.xff.wierdr; probe -25308». Ключ `AfterFirstUnlock` читается, проба нет, то есть телефон был заблокирован |

**Повтор 19.11.2026** (та же iOS 27.2.1, lab-ветка перенесена на master, Build 81). Виджет
на каждую неоткрытую печать рисует ещё две строки диагностики (`ActivitySeal.diagnose()`),
а в расширении появился виджет для экрана «Домой» (Keychain lab) с теми же строками.
Подпись проверена по `.ipa`: у виджета `keychain-access-groups:
AUL4CCB2XY.pw.xff.wierdr.shared`, профиль (wildcard) разрешает `AUL4CCB2XY.*`.

| Кто | Связка: ключ в общей группе / в любой / запись нового | Песочница |
|---|---|---|
| Live Activity (`WierdrWidgets`, pid 32706) | -25291 / -25291 / -25291 | контейнер `PluginKitPlugin`; файл в `tmp` пишется, `UserDefaults.standard` работает; `identifierForVendor` nil |
| Виджет «Домой», тот же бинарник (pid 32699) | 0 / 0 / 0, ключ прочитан | то же; `identifierForVendor` есть |
| Приложение | 0 / 0 / 0 | контейнер `Application` |

Связки ключей у Live Activity на устройстве нет совсем: ни чтения, ни записи, ни в какой
группе. Дело не в блокировке, не в подписи и не в расширении: то же расширение в виджете
«Домой» связку видит. Live Activity рисует отдельный процесс расширения в своей песочнице:
без сети, без связки ключей и без `identifierForVendor`, но со своими файлами. К тому же
выводу пришло другое приложение с Live Activity агентов, `rbstp/collie` (PR #7): «The
widget has no Keychain (errSecNotAvailable), so each notification key is mirrored in the
App Group (0600, protected until first unlock, no backup)».

**Что ещё может сработать (не проверено):**

- **App Group.** Ключ лежит файлом в общем контейнере `group.pw.xff.wierdr`. Так обычно
  передают в Live Activity картинки: приложение пишет файл, виджет читает его при
  отрисовке. Класс защиты файла по умолчанию `CompleteUntilFirstUserAuthentication`, так
  что заблокированный телефон не помеха. Признаки, что сработает: файлы песочнице Live
  Activity доступны (повтор 19.11), а collie так и делает. Нужны изменения в Apple
  Developer: группа, отдельный App ID `pw.xff.wierdr.widgets` (сейчас виджет подписан
  wildcard-профилем) и App Groups у обоих App ID. Решили пока не делать.
- **Ключ в `attributes` локально запущенной активности.** Если активность запускает само
  приложение (`Activity.request`), `attributes` не уходят в APNs, а печать `content-state`
  открывается ключом оттуда. Но так стартовать можно только из приложения на переднем
  плане, а Wierdr запускает активность пушем (push-to-start), когда агент начал работать.
- **Расшифровка в приложении.** Ключ не нужен виджету: печать открывает приложение и
  передаёт виджету открытое содержимое локальным `activity.update`. Подробно в следующем
  разделе.
- **Минимум открытым текстом.** Без печати, но в активности только счётчики и
  обезличенные строки, а подробности в приложении.

### Расшифровка в приложении

Live Activity рисует только расширение виджета, приложение само её не рисует. Но
приложение может передать виджету готовое содержимое: `activity.update(...)`, вызванный
в приложении, меняет состояние на самом телефоне, а в APNs и на релей ничего не уходит.
Обновлять и заканчивать идущую активность из фона ActivityKit разрешает, начинать нет:
старт возможен только на переднем плане или пушем (push-to-start). Ключ в этой схеме
читает приложение, а у него связка ключей работает: на iPhone оно открывало печать на
заблокированном телефоне (см. таблицу выше).

Схема: пуш Live Activity несёт печать, приложение получает его, открывает и вызывает
`activity.update` с открытым состоянием, виджет рисует его. Вопрос в том, как доставить
пуш приложению и разбудить его.

| Путь | Итог |
|---|---|
| Фоновый пуш (`content-available`) | ❌ Будит приложение, но iOS их сильно ограничивает: Apple советует не больше 2–3 в час. Приложению, которое смахнули, они не приходят. Для статусов агентов не годится |
| Notification Service Extension (видимый пуш с `mutable-content`) | ❌ Расширение получает каждый пуш и расшифровать может, но обновить Live Activity оттуда нельзя: по сообщениям на форуме Apple, в расширениях `Activity.activities` пустой (не проверено). К тому же каждый такой пуш показывает уведомление, а скрыть его можно только с entitlement `com.apple.developer.usernotifications.filtering` от Apple |
| Сам пуш Live Activity | ❓ Самый перспективный, есть признаки, что работает |

Признаки для пуша Live Activity:

- На iPhone (16.11.2026) Wierdr был свёрнут, телефон заблокирован. Приложение разбирало
  каждый запечатанный пуш: start и два update, по строке в журнале на каждый («opened in
  pw.xff.wierdr; probe -25308»). Значит, ActivityKit передаёт обновления активности
  процессу приложения и даёт ему время. Последний разбор был через ~43 с после блокировки,
  то есть позже обычного фонового времени приложения. Но это ещё не доказывает, что iOS
  будит приложение специально ради пуша.
- В симуляторе на push-to-start `liveactivitiesd` сам запустил завершённое приложение
  («Launching pw.xff.wierdr», затем «Releasing keep-alive with reason: Push token
  delivery»).

Если за это время приложение успеет открыть печать и вызвать `activity.update`,
отдельные пуши для приложения не нужны.

Не проверено:

- будит ли iOS приложение на каждый update, если оно не запущено, а не только свёрнуто;
- хватает ли этого времени на расшифровку и `update`;
- что после смахивания приложения (скорее всего, ничего не приходит);
- насколько заметно мигание: виджет сначала рисует то, что пришло в пуше, потом
  приложение подставляет открытое состояние;
- что расходует такой локальный `update` (бюджет обновлений iOS).

Чтобы схема не ломалась, если приложение не разбудили, часть данных лучше оставить
открытой. Счётчики и статусы почти ничего не раскрывают и идут открыто, а заголовки,
спейсы и модели запечатаны. Тогда виджет всегда показывает полезный обезличенный вид
(«● 1 нужен ты · ● 2 работают»), а приложение дописывает подробности, когда получает
время.

Как проверить на lab-ветке: приложение в `activityUpdates`/`contentUpdates` открывает
печать и вызывает `activity.update`, а в журнал пишет время пуша, время локального update
и состояние (свёрнуто, завершено системой, смахнуто). Считаем, на сколько пушей пришёл
локальный update и с какой задержкой. Сначала симулятор, потом iPhone.

**Размер.** zlib перед шифрованием делает пуш меньше открытого: JSON состояния сильно
повторяется.

| Состояние | Открытый `content-state` | Запечатанный |
|---|---|---|
| 3 агента | 778 Б | 597 Б |
| 8 агентов (ровно под нынешний предел `fitting`, 3000 Б) | 2983 Б | 865 Б |

Для несжимаемого текста худший случай примерно +37% (base64 и 28 Б на nonce и тег).
Поэтому `fitting` должен мерить размер уже запечатанного состояния.

**Что остаётся открытым для релея и Apple:** токен устройства, id канала, время и частота
пушей, priority, тип события (start/update/end), `stale-date` и `dismissal-date`,
`attributes-type`, IP компьютера пользователя и **текст `alert`**. Сейчас alert несёт
заголовок агента и спейс («Needs you — <заголовок> — <спейс>»). В запечатанном режиме он
должен быть общим («Needs you» / «Done» без подробностей). Где именно iOS и watchOS
показывают текст alert, нужно уточнить.

**Не проверено:**

- App Group на iPhone (см. выше).
- Расшифровка в приложении на пуш Live Activity (см. «Расшифровка в приложении»).
- Smart Stack на часах: кто разбирает состояние, если часы рисуют активность сами.
- Несколько компьютеров и смена ключа. В формат нужен `kid`, а ключи нужно хранить по
  `kid`.

**Как ключ попал бы на телефон в настоящей схеме:** `wierdr-push` создаёт ключ на Mac и
кладёт его в документ `wierdr-push` своего ядра. Приложение читает ключ при подключении
(по SSH, мимо релея) и сохраняет туда, где его видит тот, кто открывает печать: для
расшифровки в приложении хватает связки ключей приложения, для виджета на iPhone она не
подходит, кандидат App Group. Доступ к ключу есть у тех, кто может говорить с ядром, то
есть у тех же, кто и так видит агентов.

После опытов на iPhone в связке ключей (группа `AUL4CCB2XY.pw.xff.wierdr.shared`) остались
элементы лаборатории (`pw.xff.wierdr.activity-seal`: случайный ключ, проба, журнал). Они
безвредны. Удалить их можно lab-сборкой с `-sealed-lab-key delete`.

## Как повторить эксперимент

```sh
git worktree add ../wierdr-sealed-lab lab/sealed-live-activity && cd ../wierdr-sealed-lab
make project
xcodebuild -project Wierdr.xcodeproj -scheme Wierdr -derivedDataPath build/DerivedData \
  -configuration Debug -destination "platform=iOS Simulator,id=$SIM" build
xcrun simctl install $SIM build/DerivedData/Build/Products/Debug-iphonesimulator/Wierdr.app
(cd Packages/WierdrKit && swift build --product wierdr-push); P=Packages/WierdrKit/.build/debug/wierdr-push
KEY=$($P lab key)
xcrun simctl launch --console-pty $SIM pw.xff.wierdr -sealed-lab-key "$KEY"   # печатает push-to-start token
xcrun simctl terminate $SIM pw.xff.wierdr
$P lab start <token> "$KEY"            # печатает канал
$P lab update <channel> "$KEY" 1       # чужой ключ: "$($P lab key)"; без ключа: -sealed-lab-key delete
$P lab end <channel> "$KEY"
$P lab sizes
```

Посмотреть Lock Screen можно через WebDriverAgent симулятора (`POST /wda/lock`) и
`simctl io screenshot`. Первая активность придёт с вопросом «Allow Live Activities from
Wierdr?».

На iPhone: `wierdr-push` остановить (`launchctl bootout gui/$(id -u)/pw.xff.wierdr.push`,
затем `wierdr-push reset`), поставить lab-сборку и запустить приложение:
`xcrun devicectl device process launch --console … pw.xff.wierdr -- -sealed-lab-key "$KEY"`
(аргументы приложения идут после `--`). Журнал виджета читается так:
`… -- -sealed-lab-log YES`. Активность на экране видна в Notification Centre (свайп сверху
через WDA). Неоткрытая печать рисует три строки: причину, ответы связки и песочницу.
Виджет Wierdr «Keychain lab» на экране «Домой» показывает то же в своём процессе.
Приложение печатает свою диагностику при запуске (`[sealed-lab] app diag`). Потом вернуть прежнюю сборку и демон (`launchctl bootstrap gui/$(id -u)
~/Library/LaunchAgents/pw.xff.wierdr.push.plist`).
